## 零、先修正我上一轮判断的缺陷

上一轮我只从工程可行性出发，得出「不建议引入 R」。那个结论**遗漏了关键一层**：目标用户不是普通开发者，而是要交付论文插图的古生物学者。对他们来说，图的**可继续编辑性**比渲染质量更重要。

这个前提一旦加入，结论从「不要引入」变成「**要引入，但不要用 rpy2 嵌进产品**」。

---

## 一、用户真正要的是什么

关键区分：

| 产物 | 性质 | 对古生物学者的价值 |
|---|---|---|
| Python 渲染的 PNG/PDF | **终态产物**（dead end） | 改不了。期刊要求改图尺寸、换配色、加注释，只能回 PaleoAST 或找会 Python 的人 |
| R 脚本 | **源产物**（source artifact） | 数据 + 语法都在，课题组任何人都能改。改完重跑即可复现 |

这不是「R 的图更好看」——matplotlib 的渲染质量完全够。是**交付物形态**的差异：审稿人要求「把图 3 的色标改成地质年代色系」时，`.R` 脚本是 30 秒的事，PNG 是重新做一遍。

附带收益（这些才是 R 在这个领域的真正护城河）：

- **ggplot2 是语法不是函数库**——facet、分面、自由重排，Python 侧很难对等
- **期刊主题现成**：`ggthemes`、`theme_classic`、Elsevier/Springer 模板
- **多图拼版**：`patchwork` / `cowplot`，论文里的 2×3 面板
- **同行的可接手性**：实验室所有人都会 R
- **可复现性**：数据 + 脚本 = 论文附件，这是越来越多期刊的要求

## 二、三种架构的诚实成本对比

### 方案 A：rpy2 嵌入产品，运行时渲染 ggplot2

**做法**：`rpy2` 调 R，ggplot2 画图，PNG buffer 塞进 Qt 画布。

**致命约束**（来自 `pyproject.toml:65-84` 自记的失败史）：

```
"rpy2>=3.5.16,<3.6; platform_system != 'Windows'"
```

1. 最初写 `rpy2>=5.0.0`——**这个版本从未存在过**，导致装 `[dev,full]` 的 job 全部死在安装步骤，**整个 workflow 历史有 9 个 job 一直是红的**
2. rpy2 3.6.x 装上了但加载不了：`symbol 'R_getVar' not found`（R 4.3.3 已移除）
3. **Windows 上被显式排除**——而这正是本项目的开发平台**和** `PaleoAST.spec` 打包 exe 的目标平台
4. `tests/cross_validation/` 没有 rpy2 就自动跳过——R 在此项目是**测试专用**依赖
5. 那个 Cross-Validation CI job **至今仍是红的**：runner 上连 R 都装不上（`libuv not found`）

**外加**：PyInstaller 打包要带 R 运行时（每平台 ~150MB+）并锁死 ABI；R 启动 + ggplot2 渲染约 200-500ms 延迟；两套绘图实现会漂移（见第五节风险）。

**结论**：**现在不做。** 这不是技术上不可能，是它要解决的痛点（渲染质量）并不痛，而它带来的成本（打包、平台、三次失败史）全是真的。

### 方案 B：导出可继续编辑的 R 脚本 ★推荐

**做法**：PaleoAST 在导出图的同时，**额外产出一个自包含的 `.R` 脚本**，内嵌真实数据。

**关键设计点**：R 导出器读的是**结果对象**（`PCAResult` 等），不是 matplotlib 画出来的 Figure。这让它与现有 `visualization/*.py` 的 plotters **并列**而非派生，避免两套逻辑互相污染。

**产物**：
```
outputs/fig_pca_scores.pdf          ← 现有 plot_export，产品内交互
outputs/fig_pca_scores.R            ← 新增：可编辑源
outputs/fig_pca_scores.csv          ← 数据（大矩阵时用文件而非内嵌）
```

**成本**：**零打包风险**。产品不含 R，不装 rpy2，Windows 限制无关，CI 不受影响。

**捕获的价值**：上面「用户真正要的是什么」那一整节，基本全拿到。

### 方案 C：开发期 R 渲染器（仓库内预渲染）

**做法**：`scripts/render_publication_figures.R`，生成 `docs/figures/` 里的出版级图，供 README / 文档 / 论文使用。开发者本地有 R 即可。

**成本**：同样零打包风险，但产物是终态，用户改不了。**作为 B 的补充，不作为替代。**

## 三、方案 B 的落地设计

### 3.1 骨架

```
reporting/r_export.py          # 核心：R 脚本生成器
  class RScriptExporter:
      def export(result, plotter_key, output_dir) -> RExportResult

reporting/r_templates/         # 每种图一个模板
  pca_scores.R.tmpl
  pca_scree.R.tmpl
  strat_column.R.tmpl
  ...

views/ui_main_window.py        # 在"导出"菜单加一项：导出为 R 脚本
```

### 3.2 模板必须遵守的约定

这是决定成败的地方——**脚本要让人敢改**：

1. **数据优先写 `.csv` 旁边**，内嵌只在小矩阵时用（避免脚本里几万行字面量）
2. **包依赖在头部显式列出**，并注明生成时用的版本
3. **主题只在一处定义**：
   ```r
   theme_set <- theme_classic(base_size = 9)   # ← 期刊改版只改这一行
   ```
4. **标签文本不硬编码在绘图表达式里**，集中在一个 `labs()` 调用
5. **地层学约定要在脚本里注释说明**（时间轴倒置、化石名斜体）
6. **中文标签要注明字体**，R 端可能缺 CJK 字体

### 3.3 首批覆盖哪些图

按「用户最可能想改」的优先级：

| 优先级 | 图 | 理由 |
|---|---|---|
| P0 | PCA/PCoA/NMDS 得分图（含 95% 椭圆） | 生态/古生态论文的核心图，几乎每篇都要 |
| P0 | Scree 图 | 决定保留几个轴，用户常想改成 Kaiser/80%/平行分析三线并存 |
| P1 | 稀疏度曲线 + 多样性曲线 | 生态论文标配 |
| P1 | 地层柱状图 + 相关对比图 | 地层学论文核心 |
| P2 | 灭绝/存续范围图 | 带字体大小=样本量，用户常想改 |
| P2 | 异速生长图 | 形态测量学核心 |
| P3 | corrplot 式相关矩阵、pairs、马赛克图 | 上一轮盘点的空白，ggplot2 表达力优势最明显 |

### 3.4 与报告管线的衔接

`ReportBuilder.add_figure(figure_path, ...)` 接路径，**结构上已经支持 R 产出的 PDF/SVG**，不需要改。只需在导出流程里加一步「同时生成 .R」。

## 四、必须先解决的前置问题

1. **`seaborn` 不在任何 manifest**（在环境里但未声明、未真正 import）。若要用 `sns.kdeplot` / `sns.violinplot` 需先补依赖——但按方案 B 这不阻塞，R 端不依赖它。
2. **CI 的 Cross-Validation job 现在是红的**（R 装不上）。即使方案 B 不需要 CI 装 R，这个 job 也建议单独修（换 `r-base` 版本或换 base image），否则它会持续污染 CI 信号。
3. **`statsmodels` 只在 `full` extra 里**，`stratigraphy/arma.py:273` 无守卫地 import 它。裸 `pip install .` 会让 ARMA 坏掉——这与 R 无关，但是同一次「依赖清单不准确」的问题，建议一并修。

## 五、风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| **两套实现漂移** | R 脚本与 app 内图可能给出不同结果。**这正是我这轮刚修的 bug 的同款**：`min_variance` 在对话框收集了却没转发，导致 UI 显示 10 而用户要 3 | 两边**必须读同一个结果对象**；加测试断言 `.R` 里写出的数据与结果对象逐值相等 |
| 数据规模 | 大矩阵内嵌成字面量会让脚本不可读 | 阈值以上自动改写 `.csv` |
| CJK 字体 | R 端可能没有中文字体，中文标签变方块 | 模板里注明所需字体；必要时默认输出英文标签 + 中文注释 |
| 脚本可读性 | 模板生成出机器味代码，用户不敢改 | 模板手写、保持简洁，不做循环抽象 |
| 版本漂移 | ggplot2 API 变化 | 脚本头部注明生成时的 R/ggplot2 版本；模板保持只用稳定 API |

## 六、分阶段建议

**阶段 0（前置）**：修 CI 的 R 安装 job；补 `seaborn` / `statsmodels` 的依赖声明。独立价值，与本方案无关也该做。

**阶段 1（基础设施 + 2 张图）**
- `reporting/r_export.py` 骨架 + 模板机制
- PCA 得分图、Scree 图
- 测试：`.R` 数据 == 结果对象；模板能渲染出文件（若本机有 R）
- 在导出菜单加「导出为 R 脚本」

**阶段 2（扩面）**：稀疏度/多样性、地层柱、相关对比

**阶段 3（补空白）**：corrplot 式相关矩阵、pairs、马赛克图——这几张 matplotlib 表达吃力，R 优势最明显

**明确不做**（除非将来满足条件）：rpy2 嵌入运行时
- 触发条件：① 用户明确要求 app 内实时 ggplot2 渲染；② 交付方式从冻结 exe 改为包管理器/conda-forge 分发；③ CI 的 R 安装先修好。三条同时满足才重估。

---

## 七、一句话总结

**要引入 R，但引入的是「R 作为交付物形态」，不是「R 作为运行时依赖」。**
用户要的是能改的源文件，不是一张更好看的位图；给前者不需要 rpy2、不需要打包 R、不需要动 Windows 限制，也就不会重蹈那个让 9 个 CI job 长期变红的覆辙。
