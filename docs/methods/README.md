# 方法文档

这个目录回答一个具体的问题：**这个软件算出来的数，凭什么可信？**

对每一个分析，答案有四行：

| 行 | 内容 | 谁负责 |
|---|---|---|
| **假设** | 这个方法成立需要什么条件，以及哪条最常被违反 | 手写 |
| **适用条件** | 什么时候该用它、什么时候该换成另一个 | 手写 |
| **参考出处** | 原始文献，读者据此可以核对实现 | 手写 |
| **验证方式** | 这个实现被怎么验证过 | **自动生成** |

## 为什么分成两半

**假设、适用条件、参考出处**是关于**科学**的陈述，写错了只有懂行的人能发现，
所以手写。

**"验证方式"**是关于**代码**的陈述：某个分析有没有跟 R 的参考实现比对过、
有没有属性测试、有没有黄金真值。**这一栏如果靠人手维护，几个月后必然与代码脱节**——
而脱节的方式恰好是最危险的那种：表格里写着"R 已验证"，实际上没有。

所以表格由 `scripts/method_docs.py` 从 `scripts/validation_matrix.py` 的
同一份证据里生成，两边不可能不一致。

## 怎么读「验证证据」那一栏

| 标记 | 含义 | 强度 |
|---|---|---|
| **R** | 与 R 的参考实现**活跑**比对：R 在测试运行期间算出自己的答案 | 最强：两个独立实现一致 |
| **真值** | 与已发表的数据或独立推导的真值比对 | 强 |
| **性质** | 属性测试：一条对**任意**输入都成立的不变量 | 强，但只覆盖性质不覆盖数值 |
| **单元** | 在一个选定样例上返回期望值 | 必要，不充分 |

**只有「单元」的分析，是本仓库的欠账。** 它们不是错——但它们的正确性目前
只由一个样例担保。`scripts/validation_matrix.py` 会数出还有多少，
`tests/test_validation_coverage.py` 的棘轮保证这个数**只许降不许升**。

## 怎么维护

```bash
# 加了分析、改了名、或换了实现之后：
python scripts/method_docs.py               # 重写各文档里的表格
python scripts/validation_matrix.py --markdown docs/validation-matrix.md
python scripts/method_docs.py --check       # 确认没有过期（CI 会跑这个）
```

**手写部分（假设、适用条件、文献）不会被脚本覆盖**——脚本只动
`<!-- matrix:start -->` 与 `<!-- matrix:end -->` 之间的内容。

## 覆盖范围

目前覆盖 `plugins/catalog.py` 里登记的全部 **113 个一方分析**。
插件（第三方）不在此列：它们不随本仓库发布，文档由插件作者负责。

## 已知欠账

- `docs/methods/` 里的**手写**部分目前按**方法域**组织，
  逐分析的"特殊注意事项"只写了需要注意的那几个。
  其余分析的假设沿用所在域的通用假设。
- **方法文档不能替代报告规范**。写论文时还要说明：数据来源、缺失值处理、
  检验的选择理由、软件的版本号。
  这些是**用户**的责任，文档只能提供方法学上的依据。
